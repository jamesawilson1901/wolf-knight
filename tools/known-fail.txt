# 2026-09-18: dug further rather than just re-confirming. Two things this
# session's own instrumentation RULED OUT as the (sole) cause:
#   - The suites' `restCalls()` settle step ("wait 60 requestAnimationFrame
#     calls") IS provably unsound in this headless environment — a direct
#     idle probe with camera position logged every real second showed it
#     FROZEN for 13 straight real seconds, then jumping, which a fixed frame
#     count cannot account for (60 rAF calls can span under a second or
#     twenty, unpredictably). Fixed in both suites below: `restCalls()` now
#     polls `camera.position` itself until it stops moving, rather than
#     counting frames. This is a real, separate, now-fixed bug — but fixing
#     it did NOT close the gap (before/after moved from ~83/~88 to ~91/~96,
#     same 5-call delta), so it was not the whole story.
#   - Blocking narration freezing the world (js/main.js's `if
#     (narration.blocking) return`) was the FIRST suspect once the camera
#     freeze above was seen, since a caption's read-timer would explain a
#     multi-second stall exactly like it — but both suites explicitly set
#     `captions = false; voice = false` before ever touching the Den, and
#     `narration.blocking`'s own getter (js/narration.js:504) requires
#     `captions || voice` to be true. Confirmed live: `blocking` read
#     `false` for the suites' entire configuration, every sample, so this
#     is not it either.
# What remains, confirmed live with captions/voice off and the camera
